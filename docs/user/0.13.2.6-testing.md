# Version 0.13.2.6: normalisation playback compatibility

Install `pkg_audioarchive_v0-13-2-6.zip` over the current version. Re-enable playback normalisation if it was disabled for diagnosis, then reload the clip page. No waveform regeneration is needed for clips with existing current peak measurements.

## What changed

Normalised enhanced players with speed controls use decoded audio buffers and apply both playback speed and normalisation within Web Audio. They no longer connect an HTML audio element to Web Audio. This avoids the combination associated with gapped playback on the affected Safari/macOS/iPhone systems. The same approach was already used by the chromatic sampler, whose voice and recording logic is unchanged.

The unified player, playlists, and links sharing the current playback position use the same playback facade. Native audio elements and their DOM events remain available for UI integration; the original elements are not patched. Ordinary sound-board pads retain their fixed-speed streaming gain path, so this fix does not add a full-file decoding delay to recorded pad events. No original file or download is rewritten.

## On the previously affected device

1. Choose a short clip that audibly reproduced the gaps, with current waveform/peak analysis and normalisation enabled.
2. Play at 1×, then 0.5× and 0.25×. Verify continuous sound and the expected lower pitch. Change speed while playing; it should not restart the clip.
3. Pause, resume, seek with both the slider and waveform, and play through the end. Check that the cursor and displayed time track the sound at every speed.
4. Check mute and volume independently of normalisation, including after pausing and resuming.
5. Copy a link including playback position and pitch. Open it in another tab and check the starting position/speed.
6. Test automatic playlist advance and manual previous/next across normalised clips and clips with normalisation disabled. Switch tracks during initial loading; the old track must not start later.
7. Test Archive, My clips, module and administrator-preview play controls, then ordinary Sound Board pads. Test monophonic stopping during loading, chromatic MIDI/key release, and an existing recording.
8. Repeat the below-1× comparison in desktop Chrome and the previously unaffected Mac. Also test switching apps and locking/unlocking the phone; mobile background audio behaviour needs device verification.

## Loading and fallback

The first normalised playback of a clip downloads and decodes the complete protected playback source. There can therefore be a delay before sound starts, unlike native streaming. The play control can cancel a pending start. Recently decoded clips are reused within the page; pause/resume normally avoids another download.

The decoded cache is limited to 64 MiB. Downloads above 32 MiB, decoded buffers above 128 MiB, and known durations exceeding a conservative stereo estimate of that decoded budget fall back to native streaming **without normalisation**. Decoder allocation occurs before the final decoded-size check, so that check alone is not a hard bound on peak browser memory. Active polyphonic voices also need memory outside the cache. No browser-persistent audio cache is created by this implementation.

Unsupported codecs, unavailable Web Audio or refused activation also retain the ordinary native fallback. Its source remains the existing permission-checked playback endpoint. The browser element emits `audioarchive:normalizationfallback` with a diagnostic reason for developer inspection. The waveform continues to show the configured normalisation scale, as it did with earlier playback fallbacks.

## Automated verification and limits

Run `node docs/developer/tests/normalization.mjs` from the source root. It exercises the production transport against a deterministic audio-clock/media model: rates, continuous position, seek, pause/resume, replay, looping, gain/volume/mute, shared facade identity, cancellation, playlist advance, concurrent starts, cache eviction, decode/size/activation fallback and cleanup. The mock rejects any attempt to create a media-element source.

These checks verify transport logic, not audible browser output. Live Joomla and affected Safari/iPhone hardware were not available in the build environment. The device tests above remain necessary to confirm the reported regression is resolved.
